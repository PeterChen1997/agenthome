# 远程用量库：备份与重建

> CARM-284 远程用量采集（方案 A：Mac 经 SSH 拉取）的单元 6。代码在 `crates/core/src/usage_store.rs`，测试在 `crates/core/tests/usage_store.rs`。

## 两端各有什么

| 位置 | 文件 | 能不能删了重建 |
|---|---|---|
| 采集端（Runner / 其他机器） | `~/AgentHome/usage/usage.db`（SQLite，WAL）+ `~/AgentHome/device.json` | **不能**。原日志被 agent 轮转或清理后，这里是那部分花费唯一的记录 |
| Mac（汇总端） | 本机索引 `~/AgentHome/index/agenthome.db` | 可以，从本机原件重建 |
| Mac（汇总端） | 远程用量导入库 `~/AgentHome/remote/usage.db`（`crates/core/src/usage_import.rs`，与索引库分开，删索引库重建不影响它） | 可以从各采集端重拉（删掉后重新配对、游标归零），前提是采集端的库还在 |

`device.json` 里的事件键密钥决定事件键。换了密钥，同一请求会生成新的键，Mac 会把它当成新请求重复计费。所以采集端的用量库和 `device.json` **必须一起备份、一起恢复**。用量库也会记录自己属于哪个 `machine_id`，拿别的身份打开会直接报错。

## 采集端库的规则

- 一个来源文件的用量和读取进度（大小 + 修改时间）在同一个事务里提交。进程中途被停，下一轮会把这个文件重读一遍；同键同内容的记录不分配新序号，所以不会重复也不会漏。
- 每次新增或修改记录都分配单调递增的 `seq`（`meta.last_seq`，不回退、不复用）。导出端按 `seq` 分页，每个键只给出最新修订。
- 原件消失：来源标成不可见（`sources.visible = 0`），用量保留，也不产生撤回。原件回来后恢复可见，重读时不会重复计费。
- 修订：同键内容变了就整行替换，`revision + 1`。同键但时间更晚的记录视为 fork 复制，保留最早那条。
- 撤回：`UsageStore::retract` 升修订、把用量清零。之后重读到同一个键也保持撤回状态。
- 建库时生成随机的 `store_id`，导出时和游标一起给出，用来识别库是否被重建过。
- schema 版本不认识时报错，不删表。

## 备份

运行中可以直接备份，不用停服务：

```rust
store.backup_to(Path::new("/path/to/usage-backup.db"))?; // VACUUM INTO，目标必须不存在
```

也可以停掉采集服务后，把 `usage.db`、`usage.db-wal`、`usage.db-shm`（若存在）连同 `device.json` 一起拷走。不停服务时只拷 `usage.db` 不安全：最近提交的事务可能还在 WAL 里。

## 恢复与重建

- **迁机或从备份恢复**：把备份的 `usage.db` 放回 `~/AgentHome/usage/`，`device.json` 放回 `~/AgentHome/`，再启动采集。读取进度也在库里，没变的原件不会重读；之后新增的用量从 `last_seq` 往后接着编号。
- **库丢了但 `device.json` 还在**：删掉库后重新采集，仍在磁盘上的原件会生成相同的事件键。`seq` 从 1 重新开始，库标识 `store_id` 也会变。Mac 端看到 `store_id` 变了，就要对这台机器走完整快照（单元 8），不能沿用旧游标。已被清理的原件对应的用量会丢失，这就是要备份的原因。
- **两样都丢了**：按新机器处理。旧机器在 Mac 上的历史数据保留，新数据算到新的 `machine_id` 名下。
- **克隆镜像**：首次启动前删掉 `device.json` 和 `usage/`，让新机器生成自己的身份。否则两台机器会共用同一个身份。

## Mac 端导入规则（单元 7）

- 唯一键 `(machine_id, source, event_key)`；同键只接受更大的 `revision`，整行替换（撤回也是一次修订）。相同或更旧的修订忽略。
- 一页的用量和游标（对方 `store_id` + 已确认 `seq`）同一个事务提交。重复收到、旧页晚到、页内乱序、回执丢了重拉都只计一次；游标只前移。
- 页的起点超过已确认游标（缺页）整页拒收；对方 `store_id` 变了返回 `StoreReset`，交给完整快照（单元 8）。
- 配对把连接名绑定到对方 `machine_id`：本机、已配对过的机器、已占用的连接名都拒绝；连接送来的不是配对那台机器的数据也拒收。

## 采集服务：调度与资源上限（单元 10）

代码在 `crates/core/src/collector.rs`，命令是 `agenthome collect`（常驻；`--once` 只跑一轮），测试在 `crates/core/tests/collector.rs`。

| 上限 | 默认 | 参数 | 行为 |
|---|---|---|---|
| 并发 | 1 | — | 状态目录里的 `collector.lock` 加独占锁，第二个进程直接报错退出；文件逐个读，不开线程 |
| 轮次间隔 | 60 秒 | `--interval-secs` | 从上一轮开始算；有积压且没被预算卡住时立即下一轮，节奏交给限速 |
| 源读取限速 | 2 MiB/s | `--read-kib-per-sec` | 令牌桶，突发 1 秒。整文件解析的来源没法逐块限速，所以按文件大小在读之前等够额度。只看大小和修改时间的「没变」判断不计入 |
| 分片 | 64 MiB / 轮 | `--shard-mib` | 首扫和回填一轮最多读这么多，剩下的记为积压。至少读一个文件，最后一个文件可以超出分片 |
| 状态目录预算 | 512 MiB | `--state-budget-mib` | `usage/` 下所有文件合计。已用 + 32 MiB 提交预留超过预算时，先把 WAL 合并截断再量一次，仍超就暂停读新文件 |

- **续采**：每个文件的用量和进度同事务提交，进程任何时候被停，重启后只补没提交的文件。同一进程里下一轮从上一轮最后读的文件之后开始，活跃的大文件不会让后面的文件一直轮不到。
- **暂停不丢数据**：预算暂停时，没读的文件进度不前移，已有用量和待导出的变更都保留，只把积压（文件数、字节数）记进状态。腾出空间后下一轮自动继续。
- **状态与日志**：每轮把计数写进 `usage/collector-status.json`，包括读了多少、积压、是否因预算暂停、状态目录占用和失败类别。有读取、积压或失败时，向 stderr 打一行同样的计数。失败只记类别（`vanished` / `permission_denied` / `disk_full` / `io` / `unsupported` / `parse` / `store`），不写路径和报错原文。
- **来源**：来源注册表里的四个来源，再加上 OpenCode（`--opencode-root`，默认 `$XDG_DATA_HOME/opencode`）。OpenCode 只接了用量，没有登记在注册表里。
- **整文件重读的代价**：来源文件一变就整个重读。OpenCode 的库、正在写的长会话每变一次都按整个文件大小扣限速额度，所以 agent 活跃时，常态读取量取决于这些文件的大小，上限仍是 2 MiB/s。
