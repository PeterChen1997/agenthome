# 开发流水线（Pipeline）与检查清单

> 2026-11-08。任何一项功能或修复，从规格到发布都按本文的关卡走；**没过完的关卡就不算「完成」**，也不许在 `docs/10-设计落地清单.md` 里把它标成完成。
> 关卡顺序是从 P0、P1 的实际返工里总结出来的：每次跳过「真实数据」或「截图核对」，都在后面付出了更多返工（Codex 输入口径、标题栏标签重叠、列表转圈、导航位置都是这么发现的）。

## 总览

```
G0 认领 → G1 规格 → G2 数据层 → G3 界面 → G4 自动化检查 → G5 真实数据 → G6 截图核对 → G7 文档 → G8 提交 → G9 发布（按需）
```

| 关卡 | 产出 | 谁能跳过 |
|---|---|---|
| G0 认领 | 在落地清单里选定条目编号，写进提交与 TODO | 不能跳过 |
| G1 规格 | 验收标准写清楚 | 纯修 bug 可简写 |
| G2 数据层 | core 改动 + 单测 | 纯界面改动跳过 |
| G3 界面 | app 改动 | 纯数据改动跳过 |
| G4 自动化检查 | fmt / clippy / test 全过 | 不能跳过 |
| G5 真实数据 | CLI 与 app 在本机真实库上跑通 | 不能跳过 |
| G6 截图核对 | 每个受影响页面的截图，明暗各一 | 纯 core / CLI 改动跳过 |
| G7 文档 | 落地清单、功能清单、踩坑、CLAUDE.md 同步 | 不能跳过 |
| G8 提交 | 中文提交信息、引用条目编号、推送 | 不能跳过 |
| G9 发布 | 按 `docs/08-构建与发布流程.md` | 攒够一批再发 |

## G0 认领

- [ ] 在 `docs/10-设计落地清单.md` 找到条目编号（例如 `6.14`）；清单里没有的新需求，先补一行再做。
- [ ] 读该条目的「规格来源」和「缺口」两栏，打开对应的设计画板或规格文档原文，不要只看清单里的摘要。
- [ ] 查 `docs/09-开发踩坑记录.md` 对应领域的小节。
- [ ] 若条目需要改用户全局配置（如 `~/.claude/settings.json`）、碰凭据、或会删除 / 覆盖用户数据，先停下来问用户。

## G1 规格

- [ ] 写下验收标准：输入是什么、界面上应该看到什么、边界情况（无数据、来源未接入、额度文件过期、超大会话）怎么表现。
- [ ] 对照设计令牌（`docs/design/canvas.json` 的 `notes.tokens`）确认颜色、字体、间距，不现编。
- [ ] 决定数据从哪来：已有 `DataSource` 方法够不够；不够就先走 G2。
- [ ] 与设计稿不一致的地方，在 `docs/design/README.md` 的「实现与设计稿的差异」里记一行，并说明原因；需要用户拍板的先问。

## G2 数据层（core）

- [ ] 新字段先加到 `crates/core/src/model.rs`，再改 store 的 schema 与查询。
- [ ] **改了任何解析口径或表结构，升 `store.rs` 的 `SCHEMA_VERSION`**（旧库会自动重建）。
- [ ] 解析失败、未知记录类型一律计数进 Report，不静默丢弃。
- [ ] 给新逻辑写测试，fixture 用合成数据，**不要把本机真实对话内容写进仓库**。
- [ ] 测试要编码"为什么重要"：例如去重测试断言「同一 response_id 只算一次请求」，而不只是断言某个数字。
- [ ] 扩展 `DataSource` trait 时，`MockDataSource` 与 `SqliteDataSource` 必须同时实现，mock 的数据要像真的（用于截图与演示）。
- [ ] core 改了公开类型会让 app 编不过：同一提交里把 app 侧一起补齐。

## G3 界面（app）

- [ ] 写 gpui 代码前，在 `~/code_hub/_ref/gpui-kit/` 里 grep 真实签名；遵守 `skills/gpui-kit/references/coding-guides.md`。
- [ ] 稳定 `ElementId`：用会话 id、消息 id、住户 id，不用列表下标。
- [ ] IO 一律 `cx.background_spawn`，回前台写 Entity 再 `cx.notify()`；带 revision 防过期结果覆盖新结果。
- [ ] 每秒刷新的东西（倒计时）只 notify 它所在的小 Entity，不要让整页重绘。
- [ ] 颜色走主题角色（`cx.theme()`），设计令牌里有而主题没有的角色，在 `crates/app/assets/themes/pixel-habitat.json` 的明暗两套里都补上。
- [ ] 新文案用中文，数字与倒计时用 VT323，区块标题用 Pixelify Sans，正文系统字体。
- [ ] 无数据、加载中、出错三种状态都要有样子，不能空白或一直转圈。

## G4 自动化检查

```bash
cargo fmt --all --check && cargo clippy --workspace --all-targets && cargo test --workspace
```

- [ ] 三项全过，clippy 零警告（不加 `allow` 绕过，除非写明原因）。
- [ ] 测试数量只增不减；删测试要在提交信息里说明理由。

## G5 真实数据

- [ ] 改了 core：`cargo run -p agenthome-cli --release -- scan`，确认两个来源失败 0、警告 0；schema 升级时会全量重建，约 2 分钟。
- [ ] 跑与改动相关的 CLI 命令，看数字量级是否合理（例如 input 应远小于 cache_read；本月成本是几百美元而不是几万）。
- [ ] 改了 app：用 `--mock` 和真实库各启动一次，stderr 必须为空。

## G6 截图核对

- [ ] `cargo build -p agenthome-app && ./script/bundle-dev.sh && open target/AgentHome.app`。**不要用 nohup 直接跑二进制**（窗口不活动会停止重绘，见 `docs/09-开发踩坑记录.md` §5）。
- [ ] 先确认屏幕没锁，否则拿不到图。
- [ ] 每个受影响的页面截一张；改动涉及颜色的，用 `--appearance light` 与 `--appearance dark` 各截一张。
- [ ] 栖息地相关：至少覆盖受影响的状态；用 `--habitat-demo` 观察动画循环。
- [ ] 与设计画板（`docs/design/png/` 或画布）并排对比：对齐、间距、字体、颜色、文字是否截断或重叠。
- [ ] 发现问题回到 G3，修完重新走 G4 到 G6。

## G7 文档

- [ ] `docs/10-设计落地清单.md`：把条目状态改成「完成」并填上证据（`path:line`）。只有过完 G4–G6 才能改。
- [ ] `docs/03-功能清单.md`：同步状态标记。
- [ ] 新踩的坑追加到 `docs/09-开发踩坑记录.md`；发版相关的进 `docs/08-构建与发布流程.md`。
- [ ] 与设计不一致的，在 `docs/design/README.md` 记录。
- [ ] `CLAUDE.md` 的「现状」「下一步」同步；新增文档要进它的索引表。

## G8 提交

- [ ] 一个提交对应一组相关条目，信息用中文，第一行写做了什么，正文列出条目编号与验证方式。
- [ ] 推送到 `main`。不改写已推送的历史，不 force-push。

## G9 发布（按需）

- [ ] 攒够一批用户可感知的变化再发，按 `docs/08-构建与发布流程.md` 全流程：升补丁或次版本号 → `script/release-macos.sh` → 公证 Accepted → GitHub Release → 下载回来验证 Gatekeeper。
- [ ] 发布说明写「相对上一版」的变化。

## 批量开发时（多个 subagent 并行）

- [ ] 先在落地清单里按「建议的收尾顺序」划好批次，同一批内按文件拆分，**两个 agent 不改同一个文件**。
- [ ] core 与 app 并行时，core 用 `CARGO_TARGET_DIR=target/core`，避免抢 cargo 锁。
- [ ] 每个 subagent 的 brief 里写清：可改哪些文件、不能改哪些、接口签名、验证命令、返回报告的格式；要求它先读 `_ref/gpui-kit` 再写 gpui 代码。
- [ ] subagent 的报告是自述，不是证据：集成后由主 agent 自己重跑 G4–G6。
