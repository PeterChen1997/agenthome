## 1. 产品定义

**一句话：** 本机所有 AI agent 的"家"。它把散落在 `~/.claude`、`~/.codex`、`~/.gemini`、各 IDE 数据库里的对话收进一个仓库长期保存、可搜索、可分析，并把 OpenAI 与 Claude 的消耗和剩余额度放在同一块仪表盘上。

### 1.1 三个核心能力

| 能力 | 用户看到什么 | 数据从哪来 |
|---|---|---|
| **用量仪表盘** | 按天 / 周 / 月的 token 与成本趋势；按 provider、模型、项目、会话的占比；项目 → 模型 → 成本的 Sankey 流向 | 本地 transcript 的 usage 字段 + 定价表；可选 OTEL、Admin API |
| **剩余额度** | Claude 5 小时 / 7 天窗口、Codex 5 小时 / 周窗口的已用百分比与重置时间；菜单栏常驻小卡片 | Claude statusline 推送、Codex rollout 快照 / app-server；高风险端点默认关闭 |
| **对话归档仓库** | 项目树 / 时间线 / 全文搜索；单个会话的完整回放（文本、思考、工具调用、diff）；星标、标签、导出 Markdown；"用原 agent 继续这个会话" | 各 agent 本地会话文件的持久拷贝 + 规范化模型 |

### 1.2 不做什么（v0）

- 不做聊天客户端，不代理任何模型请求。
- 不做云同步服务；归档目录可以放在用户自己的同步盘，但索引库不同步。
- 不做团队 / 多用户。
- 不默认使用任何违反 ToS 的端点。

### 1.3 核心用户

就是作者自己：同时重度使用 Claude Code 与 Codex、关心额度什么时候重置、希望半年前某次对话还能翻出来并从中沉淀经验。

## 2. 存储策略：软链还是拷贝

这是用户点名要仔细想的问题。三个候选：

### 方案 A：我们的仓库软链指向原目录

只是一个"视图"，不是归档。
- Claude Code `cleanupPeriodDays` 默认 30 天删 transcript、子代理、tool-results；Gemini CLI `sessionRetention.maxAge` 默认 30 天。软链指向的文件被删，归档就空了。
- Codex 7 到 10 天后把 rollout 压成 `.jsonl.zst`，文件名变了，软链失效。
- Windows 符号链接需要开发者模式或管理员权限；iCloud / Dropbox 对软链行为不一。

**结论：A 不是归档，只能作为"预览模式"存在。**

### 方案 B：先拷贝过来，再让原目录软链回我们（用户提到的做法）

本质是把 agent 的写目录重定向到我们的仓库。看起来"一份数据两处可见"，实际上有六个硬伤：

1. **清理逻辑照样生效。** Claude Code 的清理是遍历 `~/.claude/projects` 按 mtime 删文件，它会顺着软链把我们仓库里的原件删掉。问题一个没解决。
2. **我们的仓库变成 agent 的读写热区。** agent 升级、重装、用户手动 `rm -rf ~/.claude/projects`，直接作用在归档数据上。归档的第一原则是"不被源端破坏"，这个方案正好相反。
3. **每个 agent 目录结构都不同。** Codex 是日期目录 + 两个派生 SQLite；Cursor 是单个几百 MB 到几十 GB 的 state.vscdb；OpenCode 是 SQLite + WAL。没法用一个统一的"反向软链"去接管。
4. **卸载我们的 app 时原目录变成悬空链接。** agent 可能崩溃或静默新建目录，用户在那之后产生的会话会丢。
5. **并发写没有隔离。** agent 在追加，我们在索引，同一个物理文件；SQLite 类更是不能两个进程随便开。
6. **平台与同步工具问题。** Windows junction 与 symlink 语义不同；Time Machine / 同步盘遇到目录级软链行为不可控。

**结论：绝不动 agent 的原目录。B 否决。**

### 方案 C：拷贝 + 分层仓库（采用）

原目录永远只读，我们是"旁观者 + 归档者"。仓库分三层：

```
~/AgentHome/                         # 用户可改位置；raw 层可以放同步盘
├── raw/                             # 第一层：原件，内容寻址，不可变
│   └── <provider>/<machineId>/<nativeSessionId>/
│       ├── 0001.jsonl               # 原文件的逐段快照（append-only 文件按字节段追加）
│       ├── subagents/...            # 子代理、tool-results 等附属文件
│       └── manifest.json            # 来源路径、inode、size、mtime、sha256、拷贝时间、压缩方式
├── index/                           # 第二层 + 第三层：本机专属，随时可从 raw 重建
│   ├── agenthome.db                 # SQLite：规范化模型（Session / Turn / Message / ToolCall / Usage）
│   └── agenthome.db-fts             # FTS5 全文索引（可以就在同一个 db 里）
└── user/                            # 用户产生的数据：星标、标签、笔记、导出设置
    └── annotations.db
```

- **raw 层只增不改。** append-only 文件（Claude、Codex、Copilot CLI、Pi、Aider）按 inode + byte offset 增量追加；检测到截断或替换（Claude 的 `.superseded-*` / `.orphaned-*`、Codex 压缩改名）就当作新版本整体再存一份，按 nativeSessionId 去重而不是按路径。整文件覆盖写的格式（Gemini CLI、Amp、Cline）用 mtime + size 预筛再 hash，变了才存新版本。SQLite 类（OpenCode、Goose、Cursor）用 backup API 或 `immutable=1` 只读打开，只抽会话相关的表或 KV，不整库拷贝。
- **index 层随时可重建。** 解析逻辑升级、schema 变更、换 UI 框架，都只是 `rm index && rebuild`。
- **user 层单独持久化**，重建索引不丢星标和笔记。
- **每条会话记录 `source.path`**，UI 提供"在 Finder 中显示原件"和"用原 agent `--resume`"；原件被 agent 清理后标记为"仅归档存在"。
- 空间估算：Claude Code 单会话 jsonl 通常几百 KB 到几 MB，重度用户一年几 GB；raw 层对冷数据做 zstd（Codex 自己就这么做），可忽略。

### 混合：预览模式

首次启动时允许"先看再决定"：用方案 A 的方式原地只读索引（Wake 的做法），用户确认后开启归档。默认建议开启。

### 触发时机

| 信号 | 用途 |
|---|---|
| notify 文件监听（fsevents / inotify / ReadDirectoryChangesW） | 主通道，所有 provider |
| Claude Code hooks `SessionEnd` / `Stop` / `PreCompact`（http 类型 POST 到本地服务） | 精确快照信号；transcript 写入是异步的，收到后延迟几百毫秒再拷 |
| 定时全量扫描（每小时） | 兜底，覆盖 watcher 漏事件 |

## 3. 整体架构

```
┌────────────────────────────────────────────────────────────┐
│  agenthome-app (GPUI Kit)                                   │
│  仪表盘 / 额度卡片 / 归档浏览器 / 设置 / 菜单栏            │
└──────────────┬─────────────────────────────────────────────┘
               │ Entity + background Task，不直接碰 IO
┌──────────────▼─────────────────────────────────────────────┐
│  agenthome-core                                              │
│  ├─ model      规范化会话模型、Usage、Quota                  │
│  ├─ store      raw 层写入、SQLite、FTS                        │
│  ├─ ingest     watcher 调度、增量 tail、去重、重建            │
│  ├─ pricing    定价快照 + 版本号，成本估算                    │
│  └─ registry   Provider 注册、能力声明、生命周期              │
└──────────────┬─────────────────────────────────────────────┘
               │ Provider trait（进程内）/ JSON-RPC over stdio（外部）
┌──────────────▼─────────────────────────────────────────────┐
│  providers                                                   │
│  claude-code  codex  gemini-cli  opencode  cursor  ...       │
│  statusline-quota  codex-rollout-quota  openrouter  ...      │
└────────────────────────────────────────────────────────────┘
```

设计约束：

1. **core 不依赖 gpui。** 它是一个纯 Rust crate，自带 CLI 入口（`agenthome scan / stats / export`），借 TokenMonitor 的双前端思路，也方便写测试。
2. **app 与 core 第一阶段同进程**，但 core 的公开接口按"将来可拆成 daemon"设计（借 Waku / Zeron）：所有调用都是异步、带 cancel、返回可序列化结果。
3. **所有 IO 在 background executor**，UI 线程只拿 Entity。

## 4. Provider 设计

### 4.1 两类 Provider，三种接口

| 类型 | 职责 | 典型实现 |
|---|---|---|
| `SessionProvider` | 发现并解析会话文件，产出规范化事件 | claude-code、codex、gemini-cli、opencode、cursor、copilot-cli、cline、pi、amp、aider、chatgpt-export |
| `ConsumptionProvider` | 产出 token / 成本记录（历史消耗） | 多数直接由 SessionProvider 兼任；另有 otel、anthropic-admin-api、openai-admin-api |
| `QuotaProvider` | 产出剩余额度快照 | claude-statusline、codex-rollout、codex-app-server、openrouter-key；高风险的 claude-oauth、codex-wham 默认关闭 |

```rust
// 进程内 trait（伪代码，最终以实现为准）
pub trait SessionProvider: Send + Sync {
    fn id(&self) -> ProviderId;
    fn capabilities(&self) -> Capabilities;        // 有无 usage / cost / 子代理 / 会被自动清理 / 文件语义
    fn detect(&self) -> Detection;                 // 本机有没有装、根目录在哪、版本
    fn watch_roots(&self) -> Vec<PathBuf>;         // 交给 core 的 watcher
    fn scan(&self, since: Option<Instant>) -> BoxStream<SourceFile>;   // 增量发现
    fn parse(&self, file: &SourceFile, from_offset: u64) -> BoxStream<CanonicalEvent>;  // 增量解析
}

pub trait QuotaProvider: Send + Sync {
    fn id(&self) -> ProviderId;
    fn tos_risk(&self) -> TosRisk;                 // none / low / medium / high，UI 必须展示
    fn is_available(&self) -> bool;
    fn min_interval(&self) -> Duration;
    fn fetch(&self) -> BoxFuture<Result<QuotaSnapshot>>;
}
```

### 4.2 外部 Provider 协议

内置 provider 是 workspace 里的 crate。为了让社区用任意语言接新 agent，第二阶段定义一个最小的 **子进程 JSON-RPC over stdio** 协议（传输层和 MCP / ACP 一致，便于复用心智）：

- 清单文件 `provider.json`：id、名称、版本、能力声明、启动命令。
- 方法：`initialize`、`detect`、`watch_roots`、`scan`、`parse`（流式返回 CanonicalEvent）、`fetch_quota`。
- 安装位置：`~/AgentHome/providers/<id>/`，设置页可启停。

### 4.3 规范化模型（摘要）

完整字段草案见 `docs/research/03-agent-session-formats.md` 第 4 节。关键决策：

- `Session.id = {provider}:{machineId}:{nativeId}`，多机合并靠 machineId。
- `Session.kind = main | subagent | fork | scheduled`，`parentSessionId` 保留树。
- `Message.blocks` 是统一的 ContentBlock 联合类型：text / thinking / tool_call / tool_result / image / file_ref / compaction / unknown。解析不了的留 `unknown + raw`，不丢。
- `Usage` 必须带 `inputIncludesCache` 标记：Codex、Goose 的 input 含缓存，Claude 不含，不标就会跨 agent 重复计数。
- `Cost.source = agent-reported | computed`，computed 的带 `pricingVersion`。
- Claude 同一次 API 响应会拆成多条 assistant 行（共享 `message.id` / `requestId`，各带同一份 usage），按这个 key 去重。

### 4.4 Provider 实现优先级

| 阶段 | Session | Quota | 理由 |
|---|---|---|---|
| P0 | claude-code、codex | claude-statusline、codex-rollout | 作者主力工具；两者都是 append-only JSONL，最好做；额度来源零 ToS 风险 |
| P1 | gemini-cli、opencode、pi | codex-app-server、openrouter-key | 格式清晰，有结构化 usage / cost |
| P2 | cursor、copilot-cli、cline、amp、aider、chatgpt-export | anthropic-admin-api、openai-admin-api、otel | 格式封闭或需要用户额外配置 |
| v0 不实现 | — | claude-oauth-usage、codex-wham | 未公开端点；Anthropic 明文禁止第三方使用订阅 OAuth token。已拍板 v0 不做（见 §8） |
| 不做 | windsurf、antigravity、kiro | gemini-quota、cursor-usage | protobuf 不可解析，或端点已停服 |

### 4.5 Claude 额度的合规取法（关键细节）

Claude Code `/usage` 的数据源是未公开的 OAuth 端点，第三方用它是 ToS 高风险。合规替代：Claude Code 的 **statusline** 功能会把 `rate_limits.five_hour / seven_day.{used_percentage, resets_at}` 以 JSON 推给用户配置的脚本。

做法：安装一个 statusline 包装脚本，先把 stdin `tee` 到 `~/AgentHome/signals/claude-statusline.json`，再 exec 用户原来的 statusline 命令，保证用户已有配置不受影响。局限：只在 Claude Code 运行期间更新，且仅订阅用户有这个字段。UI 要显示"N 分钟前更新"。

## 6. 技术栈与工程约定

| 项 | 选择 | 备注 |
|---|---|---|
| 语言 | Rust ≥ 1.92 | gpui-kit 的 Linux 依赖要求 |
| UI | `gpui-kit = "=0.9.0"` | 精确锁定，不直接依赖 gpui；每 3 到 4 周评估升级 |
| 数据库 | rusqlite(bundled) + FTS5 | 生态一致选择 |
| 文件监听 | notify 8 | gpui-kit 自身依赖 |
| 异步 | gpui 自带 executor 为主；core 内部用 tokio | 边界处用 channel |
| 压缩 | zstd | 读 Codex 的 .zst，也用于自家冷数据 |
| 定价表 | LiteLLM `model_prices_and_context_window.json` 内嵌快照 + 后台刷新 + pricingVersion | 未知模型显式标 unknown pricing |
| 打包 | cargo-packager（dmg / deb / AppImage / NSIS） | macOS 需 Developer ID 签名与公证 |
| 自更新 | 第二阶段，便携版用 self_update | |
| CI | 三平台构建从第一天起 | Win / Linux 标 beta |
| 构建 | debug profile 调 `opt-level = 1`，启用 `hot-reload` feature 验证 | 缓解编译时间 |

工程约定：

- core crate 零 UI 依赖，可单独 `cargo test`。
- 每个 SessionProvider 必须带脱敏的 fixture 文件和解析测试，测试要覆盖"去重、增量 offset、文件替换"三种场景。
- 任何凭据只读、不落盘、不上传；Keychain 访问失败静默跳过。
- 所有网络 provider 带真实 `User-Agent: AgentHome/<ver>`，不伪装官方客户端。

## 8. 已拍板的决策（2026-11-05）

| # | 问题 | 决定 | 影响 |
|---|---|---|---|
| 1 | 产品名与默认归档目录 | 产品名 **AgentHome**，默认归档目录 **`~/AgentHome`**（用户可改） | 用户看得见、可放同步盘；index 层仍在本机不同步 |
| 2 | ToS 高风险额度端点（Claude OAuth usage、Codex wham） | **v0 不做**，只用合规来源 | Claude 走 statusline 包装脚本；Codex 走 rollout 快照与 app-server；§4.4 中"默认关闭"一行改为"v0 不实现" |
|  | 补充（2026-11-08） | 只用桌面版的用户收不到 statusline，**改为加上「后台在伪终端运行官方 `claude` 执行 `/usage` 读屏」**（调研 A7），由用户拍板 | 不读凭据、不发对话、不耗 token；带 `--settings {"cleanupPeriodDays":36500}` 与子会话标记，避免触发清理与留下会话记录 |
| 3 | CLI / TUI 双前端 | **core 自带 CLI**（scan / stats / export），TUI P2 再评估 | core crate 必须零 UI 依赖，CLI 作为测试与调试入口 |
| 4 | 首次启动默认模式 | **默认归档**，首次启动明示预计占用空间并允许改目录 | 预览模式降级为设置页里的可选项 |
| 5 | 外部 Provider 协议 | **自定义最小协议，仅借 ACP / MCP 的 JSON-RPC over stdio 传输层** | 方法与事件按"读取历史"设计，不绑 ACP 驱动 agent 的语义；细节 P3 前定 |
