> 起因：用户觉得「现在的成本应该是偏高的」，要求分模型、分会话核对单价和缓存计价。
> 结论先行：**定价表单价与最新 LiteLLM 完全一致，缓存读、5m/1h 缓存写都按正确单价计，成本没有偏高。**
> Claude 部分比 ccusage 高 1.3%（跨会话重复的 message.id），比 Claude Code 自记的 cost-state 低 2.4%；
> Codex 部分反而**偏低约 7%**（漏了 >272k 长上下文高价档），另有 42 个归档会话没扫到。
> 数字大是因为 31.5B 缓存读 token + Opus / Fable 等高价模型，这是「等价 API 价」，不是订阅实付。

## 4. 偏差原因

1. **跨会话重复的 Claude message.id（我方偏高 $446，约 2.3%）**。fork / resume 会把历史 assistant 行复制进新文件；`claude_code.rs` 只在**单个文件内**按 message.id 去重，于是 1,569 个 message.id 出现在 2~n 个会话里（3,674 行，usage 完全相同，全在 main / subagent 同类会话间）。ccusage 全局去重，只计第一次出现。
2. **Codex 漏了 >272k 长上下文档（我方偏低 $224，约 6.9%）**。本机 2,859 次请求越过阈值（gpt-6.1-sol 2,779 次）。已在 `pricing.rs` 修正。
3. **Codex 归档会话没扫（我方偏低约 $47.5）**。`~/.codex/archived_sessions/` 有 42 个 rollout，我方只扫 `~/.codex/sessions`。
4. **ccusage 自身对新模型用回退价**：codex 报告里 gpt-6-sol / gpt-6-astra / gpt-5.6-sol / gpt-6.1-sol 在部分会话标 `isFallback: true`，这些会话 ccusage 的数字不能当真值（41 个会话 ccusage $1,748 vs 我方 $1,629）。除此之外，ccusage 对已定价会话的算法与我方修正后的口径一致（gpt-5.5 / gpt-5.4 / gpt-5.2 逐会话完全相等）。
5. **仪表盘 All 口径与分周期口径不一致**：All 优先用 cost-state、其子代理计 0（Claude $19,195），而 7 / 30 / 90 天按 `messages.cost_usd` 求和（全部时段合计 $19,498）。再叠加 cost-state 对 resume 会话的低估，All 并不比分周期「更真」。

## 5. 已修正（pricing.rs / pricing.json）

- `pricing.json` 由 LiteLLM 2026-11-09 快照重新生成（`_fetched` = 2026-11-09）：44 → 65 个模型（新增 gpt-5.x-pro / chat、claude-mythos-5 等），16 个带 `long_context` 分档。缓存读缺价时回退到输入价而不是 0。
- `Price` 新增可选 `long_context`（`above_tokens` + 五项高价）；`estimate_usd` 按单次请求的提示长度选档，整次请求（含输出）用高价，与 LiteLLM / ccusage 一致。
- `normalize_model` 支持 OpenAI 的 `-YYYY-MM-DD` 日期后缀（`gpt-5-2025-08-07` → `gpt-5`）。
- 测试：`pricing.rs` 新增「定价表单价自洽」（缓存读 ≤ 输入、1h ≥ 5m、阈值单位）；新建 `crates/core/tests/pricing_audit.rs` 6 条，每条注释写明算错的后果（缓存读按输入价放大约 9 倍、全按 5m 低估约 8%、漏 272k 档低估约 7%、合并 usage 再估会误判高价档、OpenAI 缓存二次扣减 / 推理重复计）。

生成脚本思路：取 LiteLLM 中 `litellm_provider ∈ {anthropic, openai}`、`mode ∈ {chat, responses}`、名字以 `claude- / gpt-5 / gpt-6 / o<数字>` 开头且不带日期后缀的条目，加上旧表已有名字；`*_above_<N>k_tokens` 只取标准档（忽略 batches / flex / priority）。

## 6. 需要在其他文件修的（未改，交主 agent 集成）

1. **已入库成本不会随定价表更新**（最重要）。`messages.cost_usd` 与 `sessions.estimated_cost_usd` 在 `store.rs::upsert_message_tx` / 各 provider 的 `estimate_messages` 入库时算好就冻结，换了 `pricing.json` 只有变化的文件才重算，这次的 272k 档修正对现有 Codex 数据不生效。建议：`store.rs` 记录当前 `pricing::pricing_version()`（如单行 `meta` 表或 `PRAGMA application_id` 之外的 kv），`Store::open` 发现版本变了就逐行用 token 列重算 `messages.cost_usd`（各 provider 入库口径都是 `input_includes_cache=false`，可直接用），再 `UPDATE sessions SET estimated_cost_usd = (SELECT SUM(cost_usd) …)`。**不需要升 `SCHEMA_VERSION`**，284 个已清理会话不受影响。
2. **跨会话重复 message.id**：建议在汇总查询里去重，而不是改解析（会话详情里照常显示复制来的历史）。`store.rs` 的 `stats_daily`、`stats_totals`、`stats_by_model`、`stats_by_project` 对 Claude 消息加条件「同 `native_id` 只取 `(timestamp_ms, session_id)` 最小的一行」，配 `CREATE INDEX IF NOT EXISTS idx_messages_native ON messages(native_id)`（加索引不需要重建库）。预期 Claude 合计 −$446。
3. **Codex 归档目录**：`paths.rs` 增加 `~/.codex/archived_sessions`，`providers/codex.rs` 的来源根目录与 `watch.rs` 一并纳入；同一 thread 在两处都有时按 id 去重（与 `.jsonl` / `.jsonl.zst` 并存的处理同理）。
4. **All 口径**：`store.rs::stats_totals` 的 `Period::All` 分支（`CASE WHEN s.recorded_cost_usd IS NOT NULL …`）与 `row_to_summary` 的「有 recorded 就用 recorded」——cost-state 对 resume 过的会话会低估到 1/3~1/10（见 §3.4 第 7、12 行）。建议默认显示估算（与分周期一致），cost-state 作为对照并列（即批次 1 的 6.16「估算与真值并列」），或至少取 `MAX(recorded, 父+子估算)`。
5. **调用约束**：`estimate_usd` 现在要求传单次请求的 usage。现有调用都满足（消息级；`tests/codex_fixture.rs` 的会话级比较用的是没有分档的 gpt-5 / gpt-5-codex）。以后不要对聚合后的 usage 调它；`crates/app/src/data.rs` 的 Mock 是会话级调用，只影响假数据。
